# GŌSHT — передача событий сайта в GTM

Подготовлено 18 ноября 2026 года для GTM-K4ZXKJGN и существующего GA4 G-F3DQPD2R3F, ресурс 556981530. Код сайта сохраняет единственное существующее подключение контейнера. Работы с рекламными кампаниями и основными целями Ads в этот этап не входят.

## Состояние переключения

Публичный `gtm.js` проверен чтением. В опубликованном контейнере найден Custom HTML, который устанавливает `window.__goshtMeasurementV1`, слушает клики, определяет меню по URL и ищет сообщение об успехе через MutationObserver. Триггер отправки использует регулярное выражение `^(generate_lead|click_to_call|get_directions|view_menu)$`.

Сайт по умолчанию передаёт события с префиксом `gosht_site_`, например `gosht_site_click_to_call`. Эти события предназначены для проверки в dataLayer и не совпадают с проверенным действующим триггером. Сайт передаёт канонические имена после установки `window.__goshtAnalyticsOwner = 'site-v1'`, когда старый `window.__goshtMeasurementV1` отсутствует. Очередь первых 100 событий в памяти страницы позволяет передать действия, произошедшие до загрузки новой версии GTM.

Выпуск сайта отдельно от изменения GTM безопасно оставляет текущий сбор канонических событий за legacy-обработчиком. Полные параметры филиала и серверное подтверждение заявки начинают поступать в GA4 после согласованного переключения GTM.

## Изменения аналитика в одной версии GTM

1. Открыть рабочую копию существующего GTM-K4ZXKJGN. Проверить перед публикацией, что действующие обработчики по-прежнему соответствуют описанию выше.
2. Приостановить Custom HTML «GOSHT — действия посетителя» вместе с его click/history/MutationObserver-обработчиками. Сохранить существующий Google tag и GA4 Event tag.
3. Создать Custom HTML с триггером Initialization — All Pages, один раз на страницу.

```html
<script>
  window.__goshtAnalyticsOwner = 'site-v1';
  window.dispatchEvent(new Event('gosht:analytics-ready'));
</script>
```

4. У существующего GA4 Event tag оставить имя события `{{Event}}` и один Custom Event trigger с регулярным выражением `^(generate_lead|click_to_call|get_directions|view_menu)$`. Добавить условие `analytics_source` равно `site-v1`. Проверить, что событие обрабатывает ровно один GA4 Event tag.
5. Создать Data Layer Variables версии 2 для `restaurant_id`, `language`, `cta_location`, `menu_format`, `form_id`, `lead_type`, `analytics_source`. Передать одноимённые параметры в GA4 Event tag. Не добавлять триггер для `gosht_site_.*`.
6. В GA4 создать event-scoped custom dimensions для `restaurant_id`, `cta_location`, `menu_format`, `form_id`, `lead_type`, если их ещё нет. Параметр `language` проверять в DebugView с учётом существующего одноимённого стандартного измерения. Параметр `analytics_source` нужен для фильтра передачи и диагностики.
7. Проверить новую версию в GTM Preview и GA4 DebugView, затем опубликовать изменения обработчика, флага и параметров одним выпуском GTM. Открыть новую страницу после публикации. Уже открытые страницы со старым listener сохраняют legacy-владельца до перезагрузки.

## События и параметры

| Событие после активации | Источник | Дополнительные параметры |
| --- | --- | --- |
| `click_to_call` | Клик по размеченному `tel:` выбранного филиала | — |
| `get_directions` | Клик по размеченному маршруту или ссылке карты | — |
| `view_menu` | Появление успешно открытой страницы меню либо клик по PDF | `menu_format=page` или `pdf` |
| `generate_lead` | Ответ `/api/feedback` с `ok=true` и `requestId` | `form_id=feedback`, `lead_type=feedback` |

Каждый push содержит `restaurant_id`, `language`, `cta_location`, `analytics_source=site-v1`. Допустимые идентификаторы четырёх филиалов — `mirabad`, `west`, `boulevard`, `muqimiy`. В текущей общей форме выбирается проект. Когда конкретный филиал из выбора определить нельзя, передаётся `not_selected`.

Клик по HTML-меню сохраняет место CTA в памяти. Событие `view_menu` отправляется при открытии содержимого меню. Прямой вход учитывается с `cta_location=menu_page`. Повторный эффект React, изменение категории и открытие карточки блюда на том же pathname дополнительный просмотр меню не создают. После выхода со страницы и возвращения учитывается новый просмотр.

Опциональные параметры меню и формы сбрасываются в `null` у следующего неподходящего события, чтобы dataLayer версии 2 не перенёс их от предыдущего действия. Поля формы, телефон посетителя, email, сообщение, имена файлов и идентификатор заявки в payload аналитики не включаются.

## Защита заявки от повторов

Клиент блокирует параллельную отправку через синхронный ref. Один набор введённых данных и вложений при повторной попытке использует прежний случайный `requestId`. API передаёт его в существующий Admin ingestion как idempotencyKey. При уже принятой заявке API возвращает тот же requestId и пропускает повторную отправку в Monday.

Код аналитики запоминает принятый requestId в памяти и sessionStorage текущей вкладки. Повторный ответ с тем же requestId дополнительное событие не создаёт. При недоступном sessionStorage действует проверка в памяти. Сообщение об успехе не используется как источник событий. Ошибка сервера и отклонённый запрос не создают `generate_lead`.

Обратная связь имеет `lead_type=feedback`. Форма бронирования, подтверждение брони и учёт визитов относятся к отдельному этапу P2.

## Приёмка

- На каждом из четырёх филиалов проверить телефон, PDF, маршрут, меню страницы и язык. Один клик создаёт одно соответствующее событие.
- Открыть меню напрямую, через кнопку филиала и после перехода внутри сайта. Проверить restaurant_id целевого меню.
- Принять тестовое обращение сервером с явной тестовой отметкой. Проверить один `generate_lead`, `lead_type=feedback` и отсутствие данных посетителя в dataLayer.
- Повторить ответ с тем же requestId, повторно показать сообщение об успехе и проверить ошибку API. Дополнительный лид не появляется.
- В режиме legacy проверить отсутствие второго канонического события. При принудительном сочетании owner-флага и старого marker новый код остаётся в режиме `gosht_site_`.
- После переключения проверить GTM Preview и GA4 DebugView. Локальные автоматические проверки блокируют запросы к Google и проверяют только dataLayer.

Настройки контейнера и регистрация custom dimensions передаются аналитику. Для этого этапа подтверждённая сессия редактирования GTM/GA4 не предоставлена. Изменения в кабинетах аналитики ожидают настройки и приёмки в GTM Preview/DebugView. Результаты локальной проверки фиксируются отдельно.

## Источники

Событие и параметры передаются одним `dataLayer.push`, а контейнер обрабатывает очередь сообщений последовательно. [Документация dataLayer](https://developers.google.com/tag-platform/tag-manager/datalayer)

Custom dimensions дают возможность анализировать параметры событий в отчётах. [Документация GA4](https://support.google.com/analytics/answer/14240153)

Данные посетителя исключены из аналитического payload. [Требования Google Analytics](https://support.google.com/analytics/answer/6366371?hl=ru)
